19. Methodology

The workbench evaluates the target as a black box: each test case's question is sent over HTTP (with the configured repetitions), and the normalized answer, citations, retrieved chunks, latency, and errors are persisted before any judgment is made. Evaluation then runs in two tiers:

  • Deterministic evaluators (transport, latency, required facts, forbidden claims, phrase-based refusal, citation presence, expected documents, citation–retrieval consistency, answerability) apply exact rules to the persisted evidence. They carry confidence 1.0 where matching is exact and lower confidence where phrase heuristics are involved.
  • LLM evaluators (claim extraction, groundedness, reference correctness, completeness, answer relevance, context relevance, semantic refusal, contradiction) use a local judge model with schema-enforced structured output. Scores are derived in code from the judge's per-item decisions — never taken as an unexplained number — and untrusted content is delimited so it cannot instruct the judge.

Every metric result distinguishes three outcomes: the chatbot failed the metric; the evaluator itself failed (never counted against the chatbot); or the metric was not applicable (with the reason persisted). Failure classification applies evidence-based rules (spec §16); where black-box data proves only a symptom, the finding reports the root cause as undetermined from black-box data rather than guessing. Results matching the human-review triggers (low confidence, evaluator disagreement, HIGH/CRITICAL severity, truncated context, security-sensitive tags, evaluator failures) are flagged and routed to the review queue; a human decision never deletes the automated result.

Full per-evaluator definitions, known limitations, and interpretation guidance: docs/evaluation-methodology.md in the workbench repository. Judge agreement is calibrated against a small labelled sample — an agreement rate over that sample, not "model accuracy".
