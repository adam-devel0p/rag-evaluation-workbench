# CLAUDE.md — RAG Evaluation Workbench

This file is loaded on every Claude Code session. It carries the **load-bearing constraints**.
The full specification lives in `docs/spec.md` — read it when you need detail, but the rules
below are non-negotiable and take precedence over your own defaults.

## What this project is

A local-first Spring service that **independently evaluates external chatbots and RAG systems**.
It calls a target chatbot over HTTP, captures answers/citations/chunks/latency/errors, runs
deterministic + local-LLM evaluators, flags uncertain cases for human review, classifies failure
causes, and generates an HTML reliability report. It compares a baseline run to a candidate run and
can replay stored responses through updated evaluators without re-calling the chatbot.

It is a **consultant's internal workbench**, not a SaaS platform.

## What this project is NOT (do not build)

Client document indexing, embedding generation, RAG generation, customer accounts, billing,
production monitoring agents, a general dashboard, PDF export, automatic remediation, deployment
into client infra, or compliance certification. The application evaluates *another* system; it is
not itself a chatbot or ingestion platform.

IT) · JUnit 5 · AssertJ · Mockito (only where a real/fake impl isn't more appropriate) · Docker

**Do NOT use:** Lombok · Kotlin · WebFlux (unless a strong technical reason is proven) · Kafka ·
Kubernetes · a JavaScript frontend · a vector database · authentication or multi-tenancy ·
external paid LLM APIs · automatic modification of client systems · generic AI recommendations
without evidence · unbounded asynchronous execution.

## Hard rules

- **Constructor injection everywhere.** No field injection.
- **Verify Spring AI 2.0.0 APIs before use.** Do not invent methods from older versions. When
  unsure, inspect the resolved dependency source/Javadoc or official docs and adjust until it
  compiles. This applies especially to `FactCheckingEvaluator` and `RelevancyEvaluator`.
- **Controllers contain no business logic.** Domain concepts never depend on HTTP request objects.
  Controllers never return JPA entities — use DTOs.
- **Liquibase owns the schema.** `spring.jpa.hibernate.ddl-auto: validate`. All schema changes go
  through migrations under `src/main/resources/db/changelog/`.
- **UUID identifiers generated by the application.** Timestamps as `Instant`, UTC. Enums persisted
  as strings. `@Version` optimistic locking on mutable aggregates.
- **Never persist secrets.** Store the *name* of the env var holding the secret (and optional
  API-key header name), never the value. Redact authorization headers in logs.
- **The app must build and start without Ollama.** If Ollama is down, deterministic evaluators
  still work; LLM evaluator results become `FAILED` (never a chatbot failure). `./mvnw clean verify`
  must pass with no Ollama running. Real-model tests live behind the `-Pollama-it` Maven profile.
- **Never conflate evaluator failure with chatbot failure.** Distinguish: chatbot failed the metric
  / evaluator itself failed / evaluator not applicable.
- **No score without evidence.** No unexplained scores. Don't average conflicting results into one
  misleading number. Don't claim a root cause when data only proves a symptom.
- **Privacy by default.** Don't log full prompts/answers/citations/chunks/tokens/documents. Log
  identifiers and sizes. Verbose content logging is a dev-only opt-in. No high-cardinality metric
  tags (no question text, client content, or test-case IDs as tags).

## Framework gotchas (Spring Boot 4.1 / Spring AI 2.0)

- **Jackson 3, not 2.** Spring Boot 4 / Spring AI 2.0 migrate to Jackson 3: package relocation from
  `com.fasterxml.jackson` to `tools.jackson`, and `JsonMapper` replaces `ObjectMapper`. This project
  leans heavily on Jackson tree traversal and JSON Pointer (request-template substitution, response
  extraction), so write that code against Jackson 3 imports — do not use Jackson 2 muscle memory.
- **Ollama starter name.** Use `spring-ai-starter-model-ollama`. The older
  `spring-ai-ollama-spring-boot-starter` is deprecated — do not reintroduce it if hand-editing the POM.
- **Spring AI 2.0 API surface changed** from the 1.x milestones. Verify any evaluator class
  (`FactCheckingEvaluator`, `RelevancyEvaluator`, `ChatClient`, advisors) against the resolved 2.0.0
  source/Javadoc before designing around it.

## Build & test commands

```bash
./mvnw clean verify                                   # must pass WITHOUT Ollama
./mvnw spring-boot:run -Dspring-boot.run.profiles=local,demo
./mvnw clean verify -Pollama-it                       # optional, needs Ollama + model
docker compose up -d postgres ollama
```

## Working agreement (how to operate)

- Work **one phase at a time** (see `docs/implementation-plan.md`). After each phase: run relevant
  tests, fix failures before continuing, update the implementation checklist, and record
  significant decisions in `docs/architecture.md`.
- **Do not modify passing code from earlier phases** without stating why. Prefer additive changes.
- Make sensible decisions and document them rather than pausing for approval. Ask only when
  genuinely blocked by missing information that can't be resolved safely.
- **No core-path TODOs or pseudocode.** Leave the repo runnable.

## Code quality

Clear names · small cohesive methods · immutable records for API/domain values · focused services ·
transactions at application-service boundaries · explicit validation · meaningful exception types ·
centralized exception handling (`ProblemDetail`, RFC 9457) with correlation IDs · stable enum
serialization · deterministic tests.

Avoid: god services · static global state · reflection magic · premature generic frameworks ·
unclear boolean parameters · returning null collections · swallowing/blanket-catching exceptions ·
logging sensitive content · fake implementations in production paths.
